## 15. Layer-window streaming: root cause and fix (ec4628af4)

Model: Qwen3.6-35B-A3B-UD-Q4_K_XL (256 experts, 8 used, 40 streamed layers).
Symptom: `--moe-stream-window 8` produced garbage tokens / "peg-native
format" errors on both A3B and A10B; `--moe-stream-cache 32s` byte-identical
correct.

### Evidence (instrumented runs, LLAMA_MOE_STREAM_DEBUG=1 + a GEMM-input probe)

1. The MUL_MAT_ID nodes for a layer read their pool slot tensor directly
   (src0 pointers are the real pool tensors, one per slot, ~20 MiB apart in
   the pool buffer) - the scheduler does NOT copy/snapshot the pool weights.
2. GEMMs for the first two streamed layers read nonzero data; every later
   layer read all-zero src0 (unwritten pool memory).
3. Log ordering proved the race: for il>=2 the first `DBG copy` for the
   layer landed *after* the layer's GEMM was already enqueued
   (blk.34 GEMM at log line 1042 vs first il=2 copy at line 1621).
4. A readback-memcmp probe in the remap (after the wait) showed the pool did
   not hold the layer's bytes for il>=2 (338 of 360 checks failed before the
   fix; 360/360 passed after).
5. The up-named pool tensor received exactly 2x the copies of down
   (6098 vs 3049 per tensor) and the remap verify listed it twice per layer:
   ffn_gate_exps and ffn_up_exps have equal shapes and were sharing one pool
   tensor.

### Root causes (two independent bugs)

1. Wait-skip race (primary): `prefetch_layer(il)` reserves ALL of layer il's
   slots as LOADING during layer il-1's remap (FIFO queue, so those loads run
   behind every earlier layer's loads). remap(il) then saw
   `expert_slot.size() == n_expert` (full) and skipped its resident wait
   entirely - it only waited for loads *it* had enqueued. The expert GEMMs
   were enqueued while the copies were still queued/running and read
   unwritten (zero) pool memory. Layers 0-1 appeared correct only because
   their first loads were enqueued+waited by their own remap (prefetch for
   il=1 fired early enough that its copies happened to land first).

   Note: `LLAMA_MOE_STREAM_NO_PREFETCH=1` never took effect - the window
   branch calls `prefetch_layer(sl->il + 1)` unconditionally; the env-var
   check lives in the expert branch (dead code for window mode). So the
   earlier "prefetch is not the cause" conclusion was invalid.

   Fix: in the window remap branch, always wait for all n_expert slots to be
   RESIDENT (via `expert_slot.at(e)`), regardless of whether the prefetch
   pre-reserved them.

2. Shape-keyed pool collision (secondary): pool tensors were keyed by
   (type, ne0, ne1) only, so ffn_gate_exps and ffn_up_exps (same shape on
   this arch) mapped to ONE pool tensor; the worker copied both weights into
   it at the same expert offsets - last copy wins, the other GEMM read the
   wrong weight's bytes.

   Fix: key the pool by weight role (name suffix: ffn_gate_exps /
   ffn_up_exps / ffn_down_exps / ffn_gate_up_exps) + shape, so the weights
   of one layer are distinct pool tensors while layers of equal geometry
   still share the slot machinery.

### Why the scheduler was exonerated

The scheduler handles the shared pool tensor correctly: it is a leaf with a
CUDA WEIGHTS-usage buffer, assigned to CUDA, never copied (src0 pointers in
the GEMM probe were the real pool tensors), and the CPU remap split's
CUDA->CPU ids copy forces a full CUDA sync before the remap runs. CUDA graphs
(key = cgraph->nodes[0], uid-based reuse) replay with frozen pointers but
read current memory, so the mid-graph data rewrites are safe. The corruption
was entirely within llama-moe-stream's residency logic.

### Verification

- Correctness test (--moe-stream-window 8, -p "The capital of France is",
  -n 32, -s 42, temp 0): produces "Here's a thinking process:" - output
  byte-identical to --moe-stream-cache 32s (only spinner/timing lines
  differ).
- --moe-stream-window 1: correct. LLAMA_MOE_STREAM_NO_PREFETCH=1: correct.
- --moe-stream-cache 32s (expert-slot mode): unchanged, correct.
- Pool readback verify: 360/360 layer-weight matches after the fix.
- Pool size with role-keying: 3366 -> 4694 MiB (gate tensors now distinct;
  still fits 12 GB with the 2 GB model).

## 15b. A10B window mode at pp2048: VRAM capacity limit, not a bug

Symptom: `--moe-stream-window 2` on Qwen3.5-122B-A10B crashes at pp2048/ub2048
with `CUDA error: out of memory` in `ggml_cuda_mul_mat_q` (mmq.cu, the
plain-MUL_MAT quantize launch). Small prompts (7 tokens) fine; A3B pp2048
fine (2537 t/s).

### Evidence

- The crash is at the FIRST plain attention GEMM (`blk.0.attn_qkv`
  [3072,12288]x[3072,2048]) - the MoE pool tensor is not involved at all.
- Launch config is perfectly normal (grid 2048x6x1, block 128, 0 smem, no
  pending thread or stream error, workspace only 7 MB; the VMM pool grew a
  single 8 MB chunk).
- Memory at ub2048: model 5392 MiB + expert pool 2784 MiB (W=2) + compute
  buffer 2012 MiB + KV/RS 175 MiB = ~10363 MiB of the 12 GB card. The
  compute buffer scales with ubatch (503 MiB at ub512, 2012 MiB at ub2048).
- `--moe-stream-window 1` (pool halves to 1392 MiB, total ~8971 MiB) works
  at pp2048/ub2048: 753.8 t/s, correct output.
- With the desktop sharing the physical GPU (0.7-1.8 GB), the W=2 context
  has ~0-500 MiB real headroom; the driver then fails the tiny kernel launch
  with a spurious "out of memory" (it cannot allocate launch/command
  resources at the physical limit). Context creation itself also fails at
  the 2012 MiB compute buffer when the desktop usage is high.

### Conclusion

Not a kernel, pool, or scheduler bug - the A10B at W=2/ub2048 needs
~11 GB+ of VRAM, which does not fit a 12 GB card running a desktop. W=1 is
the correct configuration on this box (same kernel path, no crash).
Documented; no code change required.

## 16. Attention-streaming window spike (rev 2 implementation)

Implements docs/attention-streaming-spike.md rev 2 (commit 08f450baf): stream the
attention projections through the window pool so nothing dense stays resident
during prefill except norms/embeddings/router.

### 16.1 Implementation (4 commits of changes, one logical change)

- Loader routing (llama-model.cpp create_tensor): in window mode, attention
  projections (ATTN_Q/K/V/OUT/QKV, "weight" suffix only) are routed to the
  window pool like the exps (host-materialize + pool-slot). Norms/embeddings/
  router stay resident. select_buft now takes the GEMM op (MUL_MAT_ID for exps,
  MUL_MAT for attention).
- Layer state (llama-moe-stream.h/.cpp): each layer gets an `attn_weights` list
  (one slab = the whole tensor, ne[2]==1) alongside the expert `weights`; the
  slot machinery sizes off the expert count (attention registers first in the
  tensor order). The worker copies attention with the layer's first expert slab
  (expert 0 item), so a layer load = attention + experts, attention first.
- Wait-op (llama-graph.cpp build_lora_mm): a no-op map_custom1 on cur gates the
  FIRST streamed attention GEMM of each layer on the pool slot's residency
  (once per layer per graph build, tracked via begin_graph_build reset). The
  previous layer's remap prefetches the slot; the wait-op itself also prefetches
  the next layer (W >= 2 only) so the load overlaps the FULL layer compute.
  Decode (n_tokens == 1) swaps attention weights to the materialized host
  tensors (same pattern as build_moe_ffn's expert swap).
- Per-layer VIEWS of the shared pool tensors for attention: the base tensor is
  shared across the layers of a window slot, which made the decode host lookup
  ambiguous (it returned the FIRST layer's host for every layer sharing the
  slot - layer 8's attention GEMM silently used layer 0's weights). Each layer
  gets a distinct view of the shared base: same memory, unambiguous identity.

### 16.2 Bugs found during bring-up (all fixed)

1. Deadlock: the attention wait-op of layer 0 is the FIRST op of the graph, but
   ensure_layer_resident_locked did not start the I/O workers (only the remap
   and prefetch did). The first wait-op enqueued loads with zero workers and
   waited forever. Fixed: start_workers_locked() in ensure_layer_resident_locked.
2. Wrong-layer decode weights (the garbage output): window pool tensors are
   shared across layers (slot = il % W), so host_for(pool_tensor) returned the
   first layer's host for every layer in the slot. Layers 8-39 decoded with
   layers 0-7's attention weights. Fixed with per-layer views (16.1).
3. W=1 corruption risk: prefetching the next layer at the wait-op (start of the
   current layer) overwrites the CURRENT layer's slot at W=1 (the slots are the
   same). The remap's prefetch (after the attention GEMMs) is the correct W=1
   trigger. Fixed: wait-op prefetch gated on W >= 2.

### 16.5 The streaming bandwidth model (how ubatch and PCIe set prefill)

The window loads EVERY layer once per ubatch (the pool rolls through the whole
model each time; no cross-ubatch caching). So the streamed bytes per ubatch are
the model's full streamable weight set, independent of ubatch size, and in the
link-bound regime:

    prefill t/s = ubatch / (streamed_bytes_per_ubatch / link_bandwidth)

i.e. prefill t/s scales LINEARLY with ubatch. The compute-bound t/s is roughly
constant across ubatch (compute scales with tokens). The crossover (link-bound
vs compute-bound) is at:  ubatch* = compute_t/s x streamed_bytes / bandwidth.

Per-model (Q4-class) saturation points (t/s where the link is exactly consumed):

| model | streamed/ubatch | PCIe3 x16 (13.5 GB/s) | PCIe4 x16 (26.9 GB/s) |
|-------|-----------------|----------------------|----------------------|
| GLM-5.3-Flash | 152 GB (76 MB/token) | 182 t/s | 362 t/s |
| DSV4-Flash | 143 GB (71.5 MB/token) | 193 t/s | 385 t/s |
| A10B / A3B | 21.6 GB (10.8 MB/token) | 1280 t/s | 2551 t/s |

The A10B/A3B are never link-bound on a real card (compute-bound at ~680/1900).
GLM/DSV4-class on a 12 GB card are forced to ub512-1024 by the compute buffer,
which caps prefill at 45-181 t/s on PCIe3 - roughly the P720's CPU parity at
the bottom. ub2048 (16 GB card) is the step that matters: 182 t/s PCIe3 (4x
the P720 CPU 31-47 t/s), 362 t/s PCIe4. ub4096 (20-24 GB) doubles it again.

### 16.6 Per-card VRAM budgets (VRAM is NOT pooled between GPUs)

Each card must independently fit: pool (W x per-layer) + resident slice +
compute buffer (which does not shrink with the layer split - the intermediates
are full-width per layer). GLM-5.3-Flash W=2 Q4_K_XL, per card:

| ubatch | pool 2x4.1 | fixed slice | compute | total | card |
|--------|-----------|-------------|---------|-------|------|
| ub512 | 8.2 | 1.5 | 0.9 | 10.6 GB | 12 GB each |
| ub1024 | 8.2 | 1.5 | 1.8 | 11.5 GB | 12 GB each |
| ub2048 | 8.2 | 1.5 | 3.6 | 13.3 GB | 16 GB each |
| ub4096 | 8.2 | 1.5 | 7.2 | 16.9 GB | 24 GB each |

Two 12 GB cards do NOT make 24 GB: each card OOMs independently. What DOES
scale with card count is the bandwidth - N cards x PCIe3 x16 stream their own
slices over their own links: 1x16G = 182, 2x16G = 364, 3x16G = 546 t/s
(until the compute cap).

### 16.7 Hardware landscape for the P720 (Gen 3 prefill box)

Every modern card negotiates down to Gen 3 x16 (15.75 GB/s); there is no
"Gen 3 native" advantage to shop for. Selection is VRAM + compute-just-above-
saturation + price:

- Tesla P40 24 GB (sm_61, ~$150-250): the budget 24 GB. No tensor cores, but
  Q4 MMQ is dp4a-based and Pascal HAS dp4a - the P40's dp4a rate (~47 INT8
  TOPS) is ~90% of a 3060's, so ~180-200 t/s GLM-class: right AT the 182 t/s
  saturation crossover (marginal; needs measuring). sm_61 is in the default
  build.
- V100 16 GB (sm_70, ~$600-900): tensor cores, in the default build, clears
  saturation comfortably, 250 W passive (P720 airflow needed).
- RTX 4060 Ti 16 GB (~$450): cheapest clean pick - modern kernels, active
  cooling, enough compute to saturate.
- RX 7900 XT 20 GB (~$1000): fits ub4096 single-card (17.2 GB) -> 364 t/s
  PCIe3, but the compute is ~3x overspec for the link and the streaming path is
  CUDA-verified only (HIP port = verification pass, not a rewrite - the
  machinery has ZERO CUDA-specific calls, it uses ggml_backend_tensor_set etc.;
  the CUDA-specific part was validating the sync/graph semantics it relies on).
- RTX 3090 24 GB: ub4096 with headroom and the CUDA-proven path, but at
  ~$2000 in this market it is bad value vs 2x 4060 Ti 16 GB (~$900, 364 t/s)
  or the 7900 XT.

Rational ladder for the P720: P40 ($200, ~182 t/s) -> 2x 4060 Ti 16 GB
(~$900, 364 t/s) -> single 20-24 GB card for ub4096 without multi-GPU.

### 16.9 ubatch tuning: max-fitting ubatch per model/W/card

The ubatch is an arbitrary parameter (llama.cpp and llama-bench accept any
value). Because the link-bound prefill is proportional to ubatch and the VRAM
grows linearly with ubatch, the optimal ubatch is the largest that fits. Max
fitting ubatch on 12 GB (compute buffer 1.34-1.79 MiB/token for hidden 4096,
0.7-0.82 for hidden 2560; bracket = n_embd scaling ^1..^2 of the A10B's
measured 503 MiB @ ub512):

| model | config | max ub on 12 GB | PCIe3 t/s at that ub |
|-------|--------|-----------------|----------------------|
| GLM-5.3-Flash | W=1 | ~3430-4580 | 266 @ub3000, ~300 @ub4000 |
| GLM-5.3-Flash | W=2 | ~1090-1450 | ~100-136 |
| DSV4-Flash | W=1 | ~4060-5430 | ~380-440 |
| DSV4-Flash | W=2 | ~2000-2670 (ub2048 works) | ~193 |
| Qwen3.8-Flash-Next | W=1/W=2 | ~10000+ | compute-bound far below the link |

Key finding: on a 12 GB card the W=1 + big-ubatch config beats W=2 + small
ubatch (the ubatch amortization of the per-ubatch stream cost outweighs the
W=2 load hiding when VRAM forces the trade). W=2 unlocks at ~ub1100-1450 for
GLM (not worth it: ~100-136 t/s), at ub2048 for DSV4 (worth it: ~193), and
trivially at ub8000+ for Qwen3.8-Flash-Next. These ranges depend on the
compute-buffer scaling constant, which the ub-scaling runs (A10B/A3B at
ub1024-8192) pin empirically.

### 17.5 Methodology lessons (this session)

- **`llama-cli` in this build is the server wrapper** — a plain `-p` invocation hangs waiting for HTTP clients (one hung run filled /tmp with 38 GB → OOM-killed the session). Oracles: `llama-server` + `/completion` (urllib), always wrapped in `timeout`.
- **`-nkvo` is a bool flag** in llama-cli/server (`-nkvo 1` = invalid argument); llama-bench accepts the value form.
- **A3B KV fits the GPU** (2 kv heads) — flash-attn + KV-offload is the correct config; `-nkvo` is only for the KV-heavy models (A10B/Hunyuan/GLM).
